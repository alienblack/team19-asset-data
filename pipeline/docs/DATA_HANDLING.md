# Data handling

## The rule

**No confidential or authorised data is committed to this repository, ever.**
Everything under `data/` is synthetic and says so in its README and its
`data_status` column. Nothing in the documentation, the notebook or the
tests quotes a real record, and the results quoted on synthetic data are
statements about the generator, not about SA Power Networks' assets.
The `.gitignore` excludes `data/private/`, `data/raw/`, `outputs/` and
`models/`; use those folders for real extracts, their results and fitted
models, and never move files out of them into tracked locations. A pull request that adds a CSV outside approved synthetic example folders should be
rejected on sight.

## Where a real extract goes

```
data/private/<extract-name>.csv          the extract as received (never modified)
outputs/<run-name>/                      pipeline outputs for that extract
models/                                  saved models (git-ignored; contain fitted forests and training statistics)
```

Run `oc-pipeline all --input data/private/<extract-name>.csv --out outputs/<run-name>`.

## What the outputs contain

The run directory reproduces the extract several times (`source_records.csv`,
`cleaned.csv`, `imputation_input.csv`, `final_imputed.csv`,
`reference_imputed.csv`) and lists individual record identifiers in
`cleaning_log.csv`, `recovery_log.csv`, `cell_provenance.csv`,
`diagnostics.csv`, `validation/low_confidence_cells.csv` and, in evaluation
mode, `evaluation/scored_cells.csv` and the partition manifest. Treat the
whole run directory with the same classification as the extract.

`report.html` embeds the profiling figures and tables (aggregates) and the
first rows of the cleaning log and the low-confidence list (record-level).
If a report is to be shared more widely than the extract, regenerate it with
`report.embed_figures: true` and remove the record-level tables, or share the
aggregate CSVs only.

A saved model (`model.joblib`) contains the fitted forests, the training
mean/median and mode of every attribute, and the category vocabularies. It
does not contain the training records, but a forest can reproduce
training-set structure to some extent; classify models with the data they
were fitted on. The provenance sidecar lists SHA-256 fingerprints of the
training identifiers, not the identifiers themselves.

## Reproducibility and audit

Every run writes `run_metadata.json` (the configuration files' hashes and
approval state, settings, software versions, timings, per-stage summaries,
the exact hyperparameters used) and `run.log`. Keep them with the outputs.
Changes made by the cleaner are logged cell by cell; years recovered from an
observed `asset_age` are logged and marked *derived*; every imputed or
derived cell of the delivered dataset is listed in `cell_provenance.csv`;
observed values are never modified (enforced by the integrity check);
nothing is filled before the imputation stage and cells outside the model
attributes are reported as unresolved rather than filled.

## Domain decisions need the data owner's approval

Some cleaning rule families are statements about the asset register rather
than about spelling: interpreting conductor-type codes as materials
(`code_mappings`), treating `0` or `9999` as unknown years (`sentinel_values`),
discarding out-of-range or unknown values. `config/overhead_conductors/cleaning_rules.yaml`
records for each family whether it needs domain approval and who approved
it. The repository ships `code_mappings` unapproved (skipped) and the other
families approved by Team 19 **for the synthetic sample only**. Before the
pipeline runs on a real extract the data owner must review these entries,
set `approved_by` to the person who decided, and re-approve the file
(`oc-pipeline config approve`). The same applies to `snapshot_year`, the
column ranges and the recovery rule in `config/overhead_conductors/data_schema.yaml`.

## Synthetic data provenance

`data/overhead_conductors/` was generated by `experiments/synthetic_data/` from aggregate,
published descriptions of an overhead-conductor population (age bands,
material and voltage shares). Its generation settings are in
`experiments/synthetic_data/config/`; the masking and defect-injection steps
are documented in `data/overhead_conductors/README.md` and reproducible with the commands
given there.
